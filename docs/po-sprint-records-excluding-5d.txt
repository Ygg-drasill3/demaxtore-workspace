# Sprint 27 — Dual Entry Workspace Architecture

## 1. Current architecture (pre-Sprint 27)

Purchase Orders were created only through RFQ (and CB/MC/BC) spawn adapters:

```
RFQ issue_po → Order Workspace spawn → createPurchaseOrderOnOrderSpawn
```

`PurchaseOrder.source` was an unstructured string (`auto` | `manual`) meaning
document generation mode, not entry path. Order workspaces always required a
parent workspace id.

## 2. Target architecture

```mermaid
flowchart TD
    A[RFQ Entry] --> C[Order Workspace]
    B[Direct PO Entry] --> C
    C --> D[Purchase Order]
    D --> E[Purchase Order Lines]
    C --> F[Order FSM]
    D --> G[PO Status and Actions]
```

Both entry paths create the **same** entities: `OrderWorkspace`, `PurchaseOrder`,
`PurchaseOrderLine`. No parallel domain models.

## 3. Domain distinction

| Domain | Role | Lifecycle SSoT |
|--------|------|----------------|
| **Purchase Order** | Commercial document | Status + `PoAction` (no FSM) |
| **Order Workspace** | Operational import execution | `order.fsm.ts` |

`PurchaseOrder.orderId` remains **unique** (1:1 with Order Workspace).

Semantic split:

- `OrderWorkspace.origin` — how the operational workspace started
- `PurchaseOrder.source` — how the commercial document was created

## 4. Prisma migration

Migration: `20260727120000_sprint27_dual_entry_po_source`

- Enum `PurchaseOrderSource`: RFQ | DIRECT | REORDER | API | LEGACY
- Enum `OrderWorkspaceOrigin`: RFQ | DIRECT_PO | REORDER | API | LEGACY
- Normalize existing `purchase_orders.source` values
- Add `order_workspaces.origin`
- Make `parent_workspace_id` / `parent_workspace_type` nullable (DIRECT_PO)
- Add list/dashboard indexes on `source` and composites

### Source mapping

| Legacy | Canonical |
|--------|-----------|
| auto, rfq | RFQ |
| manual, direct | DIRECT |
| unknown | LEGACY |

### Rollback notes

1. Drop `order_workspaces.origin`
2. Restore NOT NULL on parent columns only if no nulls exist
3. Cast `purchase_orders.source` back to TEXT; map RFQ→auto, DIRECT→manual
4. Drop enums

## 5. Source values

Canonical API output is always uppercase. Reserved for future: REORDER, API.

## 6. RFQ adapter flow

```
RFQ orchestration
  → spawnOrderWorkspace (origin=RFQ)
  → createPurchaseOrderOnOrderSpawn (adapter)
  → createPurchaseOrderForOrderTx (source=RFQ)
```

Public `issue_po` on PO actions still returns `USE_RFQ_ISSUE_PO`.

## 7. Direct internal orchestration flow

```
createDirectPurchaseOrderWorkspace(input)  // NOT public
  → $transaction
      → spawnOrderWorkspace (origin=DIRECT_PO, no parent)
      → createPurchaseOrderForOrderTx (source=DIRECT)
```

## 8. Transaction boundaries

- RFQ: existing outer RFQ transaction wraps order + PO create
- Direct: single `$transaction` for Order Workspace + PO + lines + timeline/audit
- No external network I/O inside transactions

## 9. API compatibility

Routes unchanged. Additive DTO fields:

- `PurchaseOrder.source` (canonical)
- `PoDashboardMetrics.bySource?`
- `OrderListItem.origin?`
- Order DTO: `origin`, nullable `parentWorkspaceId` / `parentWorkspaceType`

## 10. Permission enforcement

Reuses `canAccessPo` / `canAccessOrder` and existing AuthUser roles.
Direct orchestration requires actor = buyer or ADMIN/SUPER_ADMIN.

## 11. Regression test results

See unit tests:

- `packages/contracts/src/purchase-order.test.ts`
- `apps/backend/src/modules/purchase-order/purchase-order.create.test.ts`
- `apps/backend/src/modules/purchase-order/direct-purchase-order.orchestration.test.ts`

## 12. Known limitations

- No Create Purchase Order UI (Sprint 28)
- No public direct PO endpoint (Sprint 28)
- CB/MC/BC spawners use `source=LEGACY` until dedicated origins are defined
- Extra line fields (spec/packaging/unit) compose into `description` / `sku`

## 13. Sprint 28 readiness

Sprint 28 can mount a public API that calls
`createDirectPurchaseOrderWorkspace` and ship the Create PO wizard without
another domain refactor.

## Index decisions

Added because list/dashboard filter by org + status/source and buyer/supplier timelines:

- `purchase_orders(source)`
- `(organization_workspace_id, status)`
- `(organization_workspace_id, source)`
- `(buyer_id, created_at)`
- `(supplier_id, created_at)`
- `order_workspaces(origin)`

# SPR-29-01 Pre-Work — PurchaseOrderRevision Capability Audit

**Date:** 28 July 2026  
**Scope:** Documentation only — no code, schema, API, or UI changes.  
**Purpose:** Establish facts about current Purchase Order revision support so Sprint 29-01 (Revision History) can be specified against the real codebase.

---

## Executive assessment

| Area | Status |
| --- | --- |
| Prisma `PurchaseOrderRevision` model | **Exists** (Sprint 5D) |
| JSON commercial/line snapshot | **Exists** (`snapshotJson`) |
| Revision creation on PO issue | **Yes** (rev 1) |
| Revision creation on amendment approve | **Yes** (rev N) |
| Dedicated revision API endpoints | **No** |
| Dedicated RevisionService | **No** |
| Zod revision schemas | **No** |
| Frontend revision UI | **Partial** (list of number/reason/date only) |
| Snapshot compare / drawer | **No** |
| Timeline uses revision records | **No** (derived / order timeline events) |

**Readiness conclusion: Option B** — architecture partially supports Revision History. Backend already persists snapshot revisions for create + amendment approval and exposes them inside `GET /purchase-orders/:id` (`PurchaseOrderSummary.revisions`). Full Revision History UX still needs dedicated read APIs (optional but recommended), richer snapshot contracts, comparison UI, and likely snapshot completeness improvements.

---

## 1. Prisma Model

### `PurchaseOrderRevision`

**File:** `apps/backend/prisma/schema.prisma` (approx. lines 1705–1718)  
**Table:** `purchase_order_revisions`  
**Introduced by:** `apps/backend/prisma/migrations/20260615120000_sprint5d_po_management/migration.sql`

| Field | Type | Notes |
| --- | --- | --- |
| `id` | `String` UUID PK | `@default(uuid())` |
| `purchaseOrderId` | `String` UUID FK | → `PurchaseOrder.id`, `onDelete: Cascade` |
| `revisionNumber` | `Int` | Monotonic per PO |
| `createdById` | `String` UUID | Actor user id (no Prisma `@relation` to `User`) |
| `reason` | `String` `@db.Text` | Human-readable reason |
| `snapshotJson` | `Json` | Commercial + lines snapshot |
| `createdAt` | `DateTime` | `@default(now())` |

**Relationships**

- `purchaseOrder PurchaseOrder @relation(...)` — many revisions belong to one PO.
- **Does not** reference `PurchaseOrderLine` as a relation (lines are copied into JSON).
- **Does not** reference `PurchaseOrderAmendment` (amendment id is only written into order audit/timeline payloads, not as an FK on the revision row).

**Constraints / indexes**

- `@@unique([purchaseOrderId, revisionNumber])`
- No additional indexes beyond the unique constraint key.
- Cascade delete when parent PO is deleted.

### Related models (same domain)

| Model | Relevance to revisions |
| --- | --- |
| `PurchaseOrder` | Parent; has `revisions PurchaseOrderRevision[]` |
| `PurchaseOrderLine` | Live mutable lines; snapshotted into `snapshotJson.lines` |
| `PurchaseOrderAmendment` | Approval path creates a new revision; no FK back to revision |
| `PurchaseOrderAcknowledgement` | Independent; does not create revisions |

**Answers**

- Fields exist as listed above.
- The model **stores snapshots** in `snapshotJson` **plus metadata** (`revisionNumber`, `reason`, `createdById`, `createdAt`).
- It does **not** FK to lines or amendments.

---

## 2. Snapshot Capability

Snapshots are **JSON documents**, not cloned relational rows.

### Shape written at creation (`createPurchaseOrderForOrderTx`)

**File:** `apps/backend/src/modules/purchase-order/purchase-order.create.ts`

```ts
{
  header: {
    poNumber, currency, incoterm, paymentTerms, deliveryTerms, status, source,
    // + optional revisionMetadata spread (Direct PO extras)
  },
  lines: [{ sku, description, quantity, unitPrice, lineTotal }, ...]
}
```

### Shape written on amendment approval

**File:** `apps/backend/src/modules/purchase-order/purchase-order.service.ts` → `approveAmendment`

Same `header` + `lines` pattern. Status forced to `"AMENDED"`. Direct-PO `revisionMetadata` / `directLines` are **not** re-copied on amendment approval.

### Direct PO extras in rev 1

**File:** `apps/backend/src/modules/purchase-order/direct-purchase-order.orchestration.ts`

`revisionMetadata` may add into `header`:

- `expectedDeliveryDate`
- `destinationCountryCode`
- `destinationPort`
- `buyerReference`
- `notes`
- `directLines[]` (structured product fields + optional null `unitPrice`)

### Checklist

| Content | Present? |
| --- | --- |
| Complete Purchase Order row clone | **No** — selected header fields only |
| JSON snapshot | **Yes** — `snapshotJson` |
| Copied PurchaseOrderLines (as JSON) | **Yes** — `lines[]` |
| Copied documents | **No** — `documentUrl` / `documentFileName` not in snapshot |
| Copied commercial terms | **Partial** — incoterm, paymentTerms, deliveryTerms, currency; destination/notes/buyerReference only when Direct metadata was supplied on create |
| Supplier snapshot | **No** |
| Buyer snapshot | **No** |
| Metadata only | **No** — snapshots exist |

**How stored:** single Postgres `jsonb`-compatible Prisma `Json` column; application builds a plain object and persists it. Consumers (e.g. `mapSummary`, list enrichment) read the **latest** revision’s `snapshotJson` to recover Direct commercial fields / `directLines`.

---

## 3. Revision Creation

Revisions **are** created. Creation sites:

### A. Initial issuance — always rev `1`

| Item | Detail |
| --- | --- |
| File | `apps/backend/src/modules/purchase-order/purchase-order.create.ts` |
| Method | `createPurchaseOrderForOrderTx` |
| Call | `tx.purchaseOrderRevision.create({ revisionNumber: 1, ... })` |
| Reason default | `"Initial PO issuance"` (overridable via `issueReason`) |
| Triggers | Any PO create path using this helper: RFQ spawn, Direct PO orchestration, other adapters calling `PurchaseOrderService.createForOrder` |

Direct PO uses reason `"Direct Purchase Order entry"` via orchestration `issueReason`.

### B. Amendment approved — rev `N = count + 1`

| Item | Detail |
| --- | --- |

# SPR-29-03 — Operational Timeline / Event Center

**Sprint:** 29  
**Module:** Purchase Order / Order Workspace  
**Type:** Feature Enhancement  
**Date:** 28 July 2026  

## Summary

Delivered a unified Operational Timeline on the Purchase Order workspace. The timeline is a **read aggregation** over existing event producers (timeline events, revisions, commercial documents, inspection fields, shipment workspace events). No second timeline table or mutation API was introduced.

## Architecture

| Principle | Implementation |
| --- | --- |
| Timeline is a product surface | `OperationalTimelineService` normalizes DTOs only |
| Events owned by originating modules | Reads `TimelineEvent`, `PurchaseOrderRevision`, `PurchaseOrderCommercialDocument`, `OrderWorkspace` inspection fields, shipment-linked timeline rows |
| Immutable / no edit-delete | GET-only `/timeline` |
| Authorization | `canAccessPo` before aggregation |
| Actor enrichment | Single `user.findMany({ id: { in } })` batch |

## Aggregation sources

1. **TimelineEvent** on Order + Shipment workspaces (`PurchaseOrder.orderId` + `ShipmentWorkspace` children)

## Critical Issues

1. **Close / Cancel ignore PO status (state bypass)**  
   `closePo` / `cancelPo` update status with **no** `INVALID_PO_STATE` guard. A cancelled PO can be closed; a closed PO can be cancelled; terminal states are not enforced.  
   Evidence: `purchase-order.service.ts` `closePo` / `cancelPo`.  
   Violates PRR §1 (“no state transition bypass”).

2. **`po.revised` automation is configured but never fired from PO**  
   Operational Configuration seeds `po.revised` and task automation handles it, but `approveAmendment` does not call `runOperationalTaskAutomation({ type: "po.revised" })`.  
   Sprint 30 ops layer is therefore incomplete for PO revisions.

3. **Legacy Playwright `13-po-management` scenario fails**  
   Failure: supplier email lookup in `_helpers.assignAndPublish` (`Cannot read properties of undefined (reading 'id')`). Blocks confidence that RFQ→Issue PO path is still green in CI against current seed data.

---

## High Priority Issues

1. **No formal PO FSM** — transitions are ad-hoc method guards; only ack/amendment request enforce prior status. Close/cancel/reopen matrix incomplete.

2. **No optimistic locking** — `PurchaseOrder` has no `version` / If-Match. Concurrent amendment approve + another edit can race (only soft guard: one OPEN amendment).

3. **`SUPER_ADMIN` missing from `assertPoActionRole`** — routes allow SUPER_ADMIN for create/list; action matrix lists `ADMIN` but not `SUPER_ADMIN`. Platform super-admins may get `FORBIDDEN_ROLE` on close/cancel/amendment approve.

4. **`DRAFT` lifecycle incomplete** — status exists in contracts/UI filters; create defaults to **ISSUED**; no draft save/update API. “Draft kaydetme” is not production-complete.

5. **No PO reopen** — cancel/close are terminal with no reopen path (unlike Order Completion / Issues).

6. **Audit old/new values weak for PO** — `audit()` writes `fromState`/`toState` as **workspace.state**, not PO status; payload often lacks before/after line snapshots (revision snapshot exists separately on amend approve).

7. **List sort gaps** — `sort=supplier|total|expectedDeliveryDate` falls back to `issuedAt` (not true supplier/total/date sorts).

---

## Medium Priority Issues

1. **No general PO header/line PATCH** — updates only via amendment approve (by design, but product language “Güncelleme” is unmet outside amendment).

2. **Line reorder not supported** — no sequence column / reorder API.

3. **Direct PO allows `unitPrice` 0 / omitted** — amendment path requires `positive()`; create path allows nonnegative/optional → pricing semantics inconsistent.

4. **Currency validation asymmetric** — RFQ issue path: `USD|EUR|GBP`; Direct PO: any 3-letter currency. Risk of unsupported currencies downstream.

5. **Timeline naming mixed** — both `PURCHASE_ORDER_CREATED` / `PURCHASE_ORDER_ISSUED` and `po.*` styles coexist; Operational Timeline maps them, but naming is not fully standardized.

6. **Socket gap on cancel** — `po.cancelled` audit/timeline exist; no dedicated `PO_CANCELLED` socket event (close emits `PO_CLOSED`).

7. **PO soft-delete absent** — only commercial documents soft-delete; PO itself has no `deletedAt` (hard cascade from relations only).

8. **Shipment link is soft** — `ShipmentWorkspace.poRef` string, not FK; deletion/orphan behavior depends on order graph, not PO FK integrity.

9. **Operational Analytics** — no PO-specific KPI wiring found in Sprint 30-07 analytics service.

10. **PO-specific rate limiting** — router relies on global auth limits; no dedicated `/purchase-orders` limiter.

11. **Permission model ≠ Viewer / Operations / Manager / Admin** — actual roles are BUYER / SUPPLIER / ADMIN / SUPER_ADMIN (+ access via `canAccessOrder`). OPS_MANAGER / LOGISTICS_OPERATOR not in PO action matrix (may be intentional via admin portfolio, but PRR role names are not mapped).

12. **Creator filter** — list search covers PO number, supplier name/email/org, line text; dedicated “creator” filter not first-class.

## Architecture critique (senior architect lens)

Beyond bugs, a first-time senior architect would likely call out:

1. **Status as free-form string without FSM module** — Order/RFQ have stronger FSM culture; PO is the odd one out. Scale risk: every new action adds another `if` island.

2. **PO is both a commercial document and an operational hub** — workspace aggregation (timeline/docs) is powerful, but ownership boundaries blur (Order vs PO vs Shipment). Long-term, clarify aggregate root (recommend: Order owns execution; PO owns commercial commitment).

3. **Amendment = only mutation path** is architecturally clean, but product UX still implies “edit.” Either hide edit language or add controlled draft/amend flows.

4. **Revision snapshots are append-only (good)** — but live lines are destroyed/recreated, so lineage of line identity is weak for analytics and disputes.

5. **Ops configuration metadata not fully consumed** — Sprint 30 Configuration is productization; PO not fully plugged in (`po.revised`) creates false confidence that “automation is configurable.”

6. **Scalability:** list search does supplier lookup `take: 100` then `IN` filter — fine now; will degrade with large supplier directories. Prefer SQL join / full-text.

7. **Refactoring recommendation (priority order):**  
   (a) PO FSM + close/cancel guards,  
   (b) wire `po.revised`,  
   (c) optimistic lock,  
   (d) unify schemas/events,  
   (e) single architecture doc + green e2e gate.

# PRR-01 — Create Purchase Order Production Hardening

**Module:** Create Purchase Order  
**Type:** Production Readiness Remediation  
**Architecture:** Domain Hardening  
**Date:** 29 July 2026  
**Status:** COMPLETED

---

## Objective

This sprint did **not** introduce new business features.

It eliminated production blockers identified in the Production Readiness Review so the Purchase Order module can be considered production-ready.

---

## Architecture

1. Purchase Order owns its lifecycle (formal FSM).
2. Shipment never controls Purchase Order state.
3. State transitions are validated server-side.
4. Events are deterministic (`po.*` naming for new writes).
5. Timeline is append-only.
6. Audit is immutable and field-diff oriented.
7. Concurrent updates are detected via optimistic locking (`version`).
8. Existing API paths remain compatible; responses canonicalize legacy statuses.

---

## FSM

Canonical states:

| State | Meaning |
|-------|---------|
| `DRAFT` | Editable draft |
| `SUBMITTED` | Issued / awaiting acknowledgement |
| `APPROVED` | Supplier accepted (or buyer approved) |
| `IN_EXECUTION` | Active execution / after approved amendment |
| `COMPLETED` | Operationally complete |
| `CLOSED` | Terminal closed |
| `CANCELLED` | Terminal cancelled |

Legacy DB/API aliases (read-normalized):

| Legacy | Canonical |
|--------|-----------|
| `ISSUED` | `SUBMITTED` |
| `ACKNOWLEDGED` | `APPROVED` |
| `AMENDMENT_REQUESTED` | `APPROVED` |
| `AMENDED` | `IN_EXECUTION` |

Migration `20260729180000_prr01_po_fsm_hardening` adds `version` and remaps legacy status values in place.

---

## Transition Matrix

```
DRAFT        → SUBMITTED | CANCELLED
SUBMITTED    → APPROVED  | CANCELLED
APPROVED     → IN_EXECUTION | CANCELLED
IN_EXECUTION → COMPLETED | CANCELLED
COMPLETED    → CLOSED
CLOSED       → (none)
CANCELLED    → (none)
```

Shared implementation: `packages/contracts/src/purchase-order.fsm.ts`.

---

## State Guards

| Action | Allowed from | Invalid → |
|--------|--------------|-----------|
| `close_po` | `COMPLETED` only | `409 INVALID_PO_STATE` |
| `cancel_po` | `DRAFT`, `SUBMITTED`, `APPROVED`, `IN_EXECUTION` | `409 INVALID_PO_STATE` |
| `acknowledge_po` | `SUBMITTED` | `409` |
| Amendment request/approve | `APPROVED`, `IN_EXECUTION` | `409` |
| Draft edit/delete | `DRAFT` only | `409` |

Implemented in `purchase-order.policy.ts` and enforced in `purchase-order.service.ts`.

---

## Automation

Approve Amendment flow:

```
Approve Amendment
  → Revision created
  → timeline: po.amendment.approved
  → timeline: po.revised   (exactly once)
  → runOperationalTaskAutomation({ type: "po.revised" })
  → PO status → IN_EXECUTION
```

---

## Optimistic Lock

- Column: `purchase_orders.version` (default `1`)
- Mutating actions that require `version`: close, cancel, approve amendment, submit/approve/start/complete, draft PATCH
- Mismatch → `409 PO_VERSION_CONFLICT`
- Missing required version → `422 VERSION_REQUIRED`
- Frontend workspace actions always send current `version`

---

## Audit

Mutating paths now persist structured payloads including:

- `oldValue` / `newValue`
- `changedFields`
- actor / timestamp (existing audit row fields)
- `revision` (optimistic-lock version after change)

Audit rows remain append-only / immutable.

---

## Timeline

New writes use `po.*` only, e.g.:

- `po.created`, `po.submitted`, `po.approved`, `po.revised`
- `po.cancelled`, `po.completed`, `po.closed`
- `po.amendment.requested|approved|rejected`

Readers canonicalize legacy names (`PURCHASE_ORDER_ISSUED` → `po.submitted`, `po.issued` → `po.submitted`) via `canonicalizePoTimelineEvent`.

Capability matrix (platform roles) reviewed for PO actions:

| Action | Roles |
|--------|-------|

| acknowledge | SUPPLIER, ADMIN, SUPER_ADMIN |

**SUPER_ADMIN inherits all PO capabilities** (`assertPoActionRole` short-circuit).

Create / amend / close / cancel / draft update paths wrap PO row, lines, revision, timeline, and audit in a single Prisma `$transaction`. Failure rolls back — no partial Purchase Orders.
